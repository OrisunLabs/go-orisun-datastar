# Auth projection transactions

`internal/auth/project.go` applies four auth event types plus avatar, bio and header-image events through one ordered transaction. `ProjectionRepository` exposes typed state, verification facts and full-position occurrence evidence. The PostgreSQL adapter privately binds generated sqlc queries to that transaction and rejects unbound, foreign, nested and expired contexts. An owner advisory lock serializes overlapping deliveries; the subscription remains responsible for source order between batches.

Each new occurrence checks persisted evidence before strict decoding or subject-key access, loads current state, applies Go transition rules and saves state, credentials, accepted email-verification time and replay evidence before advancing. Registration cannot adopt another email, username or credential identity. Historical registration preserves later mutable facts. Missing registration and immutable token-ID collisions fail the batch. Known occurrences skip historical payload decoding, so a checkpoint retry cannot recreate credentials or tokens. Token replay retains the original expiry.

The live handler supplies singleton batches through the same API. Invalidation runs after commit, deduplicates users and recovers routing on replay after a publication failure. Composition publishes only `userId` on the existing profile channel. The independent image bridge has been removed.

`002_auth_projection.sql` defines the fresh-install auth projection. `UserRegistered` supplies `emailVerifiedAt`; SQL stores it as `email_verified_at` and requires the verification flag and timestamp to agree. Pending registration and OTP events never create auth rows or credentials. Verification carries no workflow IDs. Existing event histories and schemas are not converted automatically.

Auth reads image, bio and header-image values exclusively from `auth_user`; session, ID and login reads no longer join `profile_stats`. Composition strictly decodes profile contracts into auth-owned typed inputs without creating a reverse package dependency. `004_auth_owned_profile.sql` adds bio/header fields; the existing image field is reused. Auth persists these fields using the same user watermark and occurrence evidence, with no additional source-position columns. Account deletion, key destruction and storage cleanup retain their current behavior; replay evidence is deleted with the owning user, so this change introduces no deletion/recreation policy.

The user watermark is the single projection progress position; verification rows carry no additional position columns. Reset-token discovery retains its existing creation-time ordering. Full-position occurrence membership remains a JSON lookup without a GIN index; no receipt-only table is added. Operational creation/update timestamps are excluded from semantic partition comparisons because their defaults reflect delivery time.

Run `task test`, `task vet` and `task build`. With `TEST_DATABASE_URL` set to a disposable PostgreSQL database, native tests create isolated schemas and verify batch partition equivalence, exact replay without keys, credential/token SQL rollback, own-write visibility, pool isolation, transaction lifetime, token collisions, missing registration and preservation of accepted verification timestamps. Pure Go tests cover transition ownership, rollback, composition mapping and commit-before-publication/retry behavior. Composition PostgreSQL tests deliberately remove `profile_stats` and verify all four auth read paths, mixed auth/profile batch partitions and rollback of profile SQL failures. Native tests also prove that pending registration cannot log in and that the accepted registration fact alone creates a verified account. No application reset or reseed was executed.

Password changes are projected exclusively from `PasswordChanged`. Reset authorization and completion are workflow facts; neither updates credentials or advances the effective user watermark. Native tests deliver completion before the effective fact to verify that login still requires the old password until `PasswordChanged` is applied.

Auth erasure retains a permanent `auth_erased_users` marker with only the user ID and occurrence evidence. Cleanup acquires the same auth advisory transaction lock as projection writes, transfers existing occurrence receipts into the marker and removes auth rows in one transaction, before the deletion command destroys the key. A failed cleanup rolls back the marker and row removal together. Projection saves reject erased identities under that same lock.

For an unseen occurrence, the projector strictly decodes the owning contract to identify its user before key access. A marked user gets an occurrence receipt without decrypting or recreating user, credential or verification rows. Auth-owned profile inputs use a composition-supplied strict owner decoder. Missing keys without an erasure marker remain errors. Previously recorded occurrences retain their existing key-free replay path, including after row removal. Notification retries use the retained routing evidence after commit. The fixed auth source boundary and full commit/prepare pair identify each occurrence; UUID reuse does not deduplicate distinct occurrences.

Migration `005_auth_erased_users.sql` creates the marker table and GIN indexes for JSON occurrence-existence lookups on both active and erased users; marker lookup/update uses its primary key. No migration or reset is run against application data automatically. Native tests cover delayed encrypted and plaintext auth inputs, erased registration not yet projected, active-user progress, strict malformed-event rejection, skipped-receipt rollback, cleanup rollback, lock contention, notification retry, and composed profile inputs. Profile and todo projections retain their existing behavior and need their own erasure conversion.
