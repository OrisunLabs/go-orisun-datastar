# Auth projection transactions

`internal/auth/project.go` applies seven auth event types plus avatar, bio and header-image events through one ordered transaction. `ProjectionRepository` exposes typed state, verification facts and full-position occurrence evidence. The PostgreSQL adapter privately binds generated sqlc queries to that transaction and rejects unbound, foreign, nested and expired contexts. An owner advisory lock serializes overlapping deliveries; the subscription remains responsible for source order between batches.

Each new occurrence checks persisted evidence before strict decoding or subject-key access, loads current state, applies Go transition rules and saves state, credentials, optional verification input and replay evidence before advancing. Registration cannot adopt another email, username or credential identity. Historical registration preserves later mutable facts. Missing registration and immutable token-ID collisions fail the batch. Known occurrences skip historical payload decoding, so a checkpoint retry cannot recreate credentials or tokens. Token replay retains the original expiry.

The live handler supplies singleton batches through the same API. Invalidation runs after commit, deduplicates users and recovers routing on replay after a publication failure. Composition publishes only `userId` on the existing profile channel. The independent image bridge has been removed.

`002_auth_projection.sql` is an idempotent additive migration. It retains existing login rows, credentials, verification flags and operational timestamps. New email validation facts contain validation ID, OTP ID and time together; SQL rejects partial facts. Existing verified users need no synthetic historical validation fact. Pre-migration rows start with unknown user watermarks (`NULL` pairs) and empty occurrence evidence. Earlier checkpointed history is not automatically replayed or backfilled. The migration does not reset data or checkpoints. Existing token inputs retain their original expiry when a matching source occurrence is replayed.

Auth reads image, bio and header-image values exclusively from `auth_user`; session, ID and login reads no longer join `profile_stats`. Composition strictly decodes profile contracts into auth-owned typed inputs without creating a reverse package dependency. `004_auth_owned_profile.sql` adds bio/header fields; the existing image field is reused. Auth persists these fields using the same user watermark and occurrence evidence, with no additional source-position columns. Account deletion, key destruction and storage cleanup retain their current behavior; replay evidence is deleted with the owning user, so this change introduces no deletion/recreation policy.

The user watermark is the single projection progress position; verification rows carry no additional position columns. Reset-token discovery retains its existing creation-time ordering. Full-position occurrence membership remains a JSON lookup without a GIN index; no receipt-only table is added. Operational creation/update timestamps are excluded from semantic partition comparisons because their defaults reflect delivery time.

Run `task test`, `task vet` and `task build`. Composition PostgreSQL tests deliberately remove `profile_stats` and verify all four auth read paths, mixed auth/profile batch partitions and rollback of profile SQL failures. Native tests apply the additive migration twice. For an existing installation, the additive migration does not backfill bio/header facts that precede the current auth checkpoint. Rebuild the auth read model from the merged event history as a coordinated deployment step; merely rewinding its checkpoint against existing watermarks will not backfill older facts.
